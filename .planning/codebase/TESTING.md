## Test File Placement

**The most important rule: tests follow the code, not the app.**

| What you're testing | Where the test lives | Environment | Why |
|---|---|---|---|
| Shared business logic (stores, queries, hooks) | `packages/core/*.test.ts` | Node (no DOM) | No DOM needed, pure logic |
| Shared UI components (pages, forms, modals) | `packages/views/*.test.tsx` | jsdom | Needs DOM, no framework mocks |
| Platform-specific wiring (cookies, redirects, searchParams) | `apps/web/*.test.tsx` or `apps/desktop/` | jsdom + framework mocks | Needs `next/navigation` or `react-router-dom` mocks |
| End-to-end user flows | `e2e/*.spec.ts` | Real browser (Playwright) | Real backend + frontend |

**Never test shared component behavior in an app's test file.** If a test requires mocking `next/navigation` or `react-router-dom` to test a component from `@multica/views`, the test is in the wrong place — move it to `packages/views/` and mock `@multica/core` instead.

## Mocking Conventions

### Zustand Stores (vi.hoisted pattern)

Zustand stores are both callable functions and have `.getState()`. Mock them with `vi.hoisted()` + `Object.assign`:

```typescript
// In packages/views/ tests:
vi.mock("@multica/core/auth", () => ({
  useAuthStore: Object.assign(
    (selector?: any) => {
      const state = { user: mockAuthUser, isAuthenticated: true };
      return selector ? selector(state) : state;
    },
    { getState: () => ({ user: mockAuthUser, isAuthenticated: true }) },
  ),
  registerAuthStore: vi.fn(),
  createAuthStore: vi.fn(),
}));
```

### API Client Mocking

Mock `@multica/core/api` for API calls. Use `vi.hoisted()` to declare mock functions before the `vi.mock` call:

```typescript
const mockListIssues = vi.hoisted(() =>
  vi.fn().mockResolvedValue({ issues: [], total: 0 })
);
const mockListGroupedIssues = vi.hoisted(() =>
  vi.fn().mockResolvedValue({ groups: [] })
);

vi.mock("@multica/core/api", () => ({
  getApiClient: () => ({
    listIssues: mockListIssues,
    listGroupedIssues: mockListGroupedIssues,
  }),
}));
```

### API Instance Shim (core tests)

For `packages/core/` tests that test query functions, use `setApiInstance` with a type-only shim:

```typescript
function installFakeApi(listIssues: (params?) => Promise<ListIssuesResponse>) {
  setApiInstance({ listIssues } as unknown as ApiClient);
}
```

### Navigation Mocking (views tests)

In `packages/views/` tests, mock the local navigation module — never mock `next/*` or `react-router-dom`:

```typescript
vi.mock("../../navigation", () => ({
  AppLink: ({ children, href, ...props }: any) => (
    <a href={href} {...props}>{children}</a>
  ),
  useNavigation: () => ({ push: vi.fn(), pathname: "/issues" }),
  NavigationProvider: ({ children }: { children: React.ReactNode }) => children,
}));
```

### Framework-Specific Mocking (web tests)

In `apps/web/` tests, mock `next/navigation` for platform-specific behavior:

```typescript
vi.mock("next/navigation", () => ({
  useRouter: () => ({ push: vi.fn(), replace: vi.fn() }),
  usePathname: () => "/login",
  useSearchParams: () => searchParamsState.params,
}));
```

### I18n Wrapper for Tests

Component tests that render UI need an i18n provider wrapper:

```typescript
import { I18nProvider } from "@multica/core/i18n/react";
import enCommon from "../../locales/en/common.json";

const TEST_RESOURCES = { en: { common: enCommon, issues: enIssues } };

function I18nWrapper({ children }: { children: ReactNode }) {
  return (
    <I18nProvider locale="en" resources={TEST_RESOURCES}>
      {children}
    </I18nProvider>
  );
}

function renderWithI18n(ui: ReactElement) {
  return render(ui, { wrapper: I18nWrapper });
}
```

### What to Mock

- `@multica/core/auth` — auth store (always)
- `@multica/core/api` — API client methods
- `@multica/core/hooks` — `useWorkspaceId` (returns `"ws-1"`)
- `@multica/core/paths` — `useCurrentWorkspace`, `useWorkspacePaths`
- `../../navigation` — `AppLink`, `useNavigation`, `NavigationProvider`
- `sonner` — toast notifications
- Heavy child components that aren't under test (return `null`)

### What NOT to Mock

- **In `packages/views/` tests:** NEVER mock `next/*` or `react-router-dom` — those don't exist here.
- **In `packages/views/` tests:** NEVER mock `@multica/views/*` — test the real component.
- **In `packages/core/` tests:** No DOM mocks needed (Node environment).

## TDD Workflow

1. **Write a failing test** in the correct package (see placement table above).
2. **Write the implementation** to make the test pass.
3. **Run `pnpm test`** — Turborepo discovers all packages with test scripts.
4. **Green = done.**

For targeted iteration during development:
```bash
# Single package
pnpm --filter @multica/core exec vitest run path/to/test.test.ts

# Watch mode for a package
pnpm --filter @multica/views exec vitest watch
```

## Test Infrastructure Details

### packages/core/ (Node environment)

- Vitest with `globals: true`, no DOM.
- Tests for: Zustand stores, query functions, API client, utility functions, path resolution, permissions, i18n.
- No setup file needed.
- Mock API via `setApiInstance()` or `vi.stubGlobal("fetch", ...)`.

### packages/views/ (jsdom environment)

- Vitest with `@vitejs/plugin-react`, jsdom environment.
- Setup: `@testing-library/jest-dom/vitest`, localStorage stub, matchMedia stub, ResizeObserver stub, elementFromPoint stub.
- Tests for: shared business pages, forms, dialogs, editors, layout components.
- Uses `@testing-library/react` (`render`, `screen`, `waitFor`, `fireEvent`).
- Uses `@testing-library/user-event` for interaction simulation.
- Always wrap rendered components with `I18nProvider` and `QueryClientProvider`.

### apps/web/ (jsdom environment)

- Vitest with `@vitejs/plugin-react`, jsdom environment, path aliases (`@/`, `@core`).
- Setup: `@testing-library/jest-dom/vitest`, ResizeObserver stub, localStorage mock with `vi.fn()`.
- Tests for: Next.js page wiring, platform-specific behavior (cookies, redirects, searchParams).
- Mocks `next/navigation` for router, `usePathname`, `useSearchParams`.

### apps/desktop/ (jsdom environment)

- Vitest with `@vitejs/plugin-react`, jsdom environment, alias `@` → `src/renderer/src`.
- Tests for: Electron-specific wiring, desktop navigation adapter.
- `passWithNoTests: true`.

### server/ (Go standard testing)

- Standard `go test ./...`.
- Tests use a real PostgreSQL database (`DATABASE_URL` env var, defaults to `postgres://multica:multica@localhost:5432/multica`).
- `TestMain` pattern: connect to DB, set up fixtures, run tests, clean up fixtures.
- Skip gracefully if database unavailable: `t.Skip("database not available")`.
- Handler tests create their own fixture data (users, workspaces, agents, issues).
- Fixtures cleaned up in `cleanupHandlerTestFixture` after test suite.
- `httptest.NewRequest` + `httptest.NewRecorder` for HTTP handler testing.
- Rate limiters set to generous defaults in tests to avoid interference between test cases.

### e2e/ (Playwright)

- Self-contained tests using `TestApiClient` for data setup/teardown.
- Login via API (send-code → DB read → verify-code → inject token into localStorage).
- `TestApiClient` class in `e2e/fixtures.ts` — raw fetch, zero build-time coupling to web app.
- `loginAsDefault(page)` helper in `e2e/helpers.ts` — authenticates and navigates to workspace.
- `test.beforeEach` creates API client + logs in; `test.afterEach` calls `api.cleanup()`.
- Tests create their own fixture data via API (e.g., `api.createIssue("Test Issue")`).

## API Response Contract Tests

Every new or changed endpoint must have at least one test that feeds a malformed response through its schema. Example from `packages/core/api/schema.test.ts`:

```typescript
it("falls back to an empty array when the body is null", async () => {
  stubFetchJson(null);
  const client = new ApiClient("https://api.example.test");
  const entries = await client.listTimeline("issue-1");
  expect(entries).toEqual([]);
});

it("accepts a new entry type rather than crashing on enum drift", async () => {
  stubFetchJson([{ type: "future_kind", id: "e-1", ... }]);
  const client = new ApiClient("https://api.example.test");
  const entries = await client.listTimeline("issue-1");
  expect(entries[0]?.type).toBe("future_kind");
});
```

These tests are the contract defense for the installed-app architecture — an Electron build on a user's laptop cannot be hotfixed like a browser app.

## Common Patterns Summary

| Pattern | When to use |
|---|---|
| `vi.hoisted(() => vi.fn())` | Mock functions that need to be referenced before `vi.mock` runs |
| `Object.assign(selectorFn, { getState })` | Zustand store mocks (callable + `.getState()`) |
| `setApiInstance({...} as unknown as ApiClient)` | Core query tests with fake API |
| `stubFetchJson(body, status)` | API client schema fallback tests |
| `I18nProvider` wrapper | Any views/web component test that renders UI text |
| `QueryClientProvider` wrapper | Any test that uses TanStack Query hooks |
| `t.Skip("database not available")` | Go handler tests when DB is unreachable |
