## Code Style

### TypeScript

- **Strict mode** enabled across all packages (`"strict": true` in tsconfig).
- Keep types explicit — never rely on implicit `any`.
- ESLint with `typescript-eslint` recommended config + `eslint-plugin-import-x`.
- No Prettier / Biome — linting only. Formatting is enforced by ESLint rules and developer discipline.
- `@typescript-eslint/no-unused-vars: off` — enforced by TS compiler (`noUnusedLocals`/`noUnusedParameters`) instead.
- `@typescript-eslint/no-explicit-any: off` — `any` allowed where needed.
- React Hooks rules (`react-hooks/exhaustive-deps`) apply to `.ts` files too, not just `.tsx`.
- i18next plugin enforces no raw JSX text in `packages/views/` (see i18n section below).

**ESLint config hierarchy:**
- `packages/eslint-config/base.js` — shared base (TS + import-x/no-extraneous-dependencies)
- `packages/eslint-config/react.js` — adds React + React Hooks plugins
- `packages/eslint-config/next.js` — adds Next.js plugin
- Each package/app has its own `eslint.config.mjs` extending from these

### Go

- **Standard `gofmt` + `go vet`** — no exceptions.
- Handler files mirror domain names: `agent.go`, `auth.go`, `runtime.go`.
- Tests colocated as `<file>_test.go`.
- CI runs `go build ./...` then `go test ./...` against a real `pgvector/pgvector:pg17` database.

## Commit Conventions

**Format:** Conventional Commits

```
<type>(<scope>): <description>
```

**Types:**
- `feat(scope)` — new feature
- `fix(scope)` — bug fix
- `refactor(scope)` — code restructuring without behavior change
- `docs` — documentation only
- `test(scope)` — adding or modifying tests
- `chore(scope)` — tooling, CI, dependency updates

**Rules:**
- Atomic commits grouped by logical intent.
- One logical change per commit — don't mix feature work with refactoring.

## CSS Architecture

### Tailwind CSS

- **Tailwind v4** across all apps (web, desktop, mobile uses its own config).
- No standalone `tailwind.config.*` for web/desktop — Tailwind v4 uses CSS-based config via `@theme inline` in `packages/ui/styles/tokens.css`.
- `@source` directives in app CSS scan shared packages so Tailwind sees all class names.

### Design Tokens

- **Always use semantic tokens** from `packages/ui/styles/tokens.css`:
  - `bg-background`, `text-foreground`, `bg-card`, `text-muted-foreground`
  - `border-border`, `ring-ring`, `bg-primary`, `text-primary-foreground`
  - `bg-accent`, `text-accent-foreground`, `bg-destructive`, `text-destructive`
  - `bg-success`, `bg-warning`, `bg-info`, `bg-brand`
  - Sidebar tokens: `bg-sidebar`, `text-sidebar-foreground`, `bg-sidebar-accent`
  - Chart tokens: `text-chart-1` through `text-chart-5`
  - Radius tokens: `rounded-sm`, `rounded-md`, `rounded-lg`, `rounded-xl`
- **Never use hardcoded Tailwind colors** (`text-red-500`, `bg-gray-100`). Always semantic tokens.
- Color values use `oklch()` format.

### Shared Styles

- `packages/ui/styles/base.css` — shared keyframes, animations, scrollbar styling, Shiki dual themes.
- `packages/ui/styles/tokens.css` — all design tokens (imported by every app).
- Never duplicate scrollbar styling, keyframes, or base layer rules in app CSS.

### Utilities

- `tailwind-merge` — merge conflicting Tailwind classes.
- `clsx` — conditional class composition.
- `class-variance-authority` — variant-based component styling (shadcn pattern).

## Component Patterns

### shadcn / Base UI

- **Prefer shadcn components** over custom implementations.
- Install via `pnpm ui:add <component>` — adds to `packages/ui/components/ui/`.
- All components use **Base UI primitives** (`@base-ui/react`), NOT Radix.
- Config: `packages/ui/components.json` (Base UI variant, base-nova style).

### Shared vs Platform-Specific

- **`packages/ui/`** — atomic UI components, zero business logic, zero `@multica/core` imports.
- **`packages/views/`** — shared business pages/components, zero `next/*` or `react-router-dom` imports.
- **`apps/web/app/`** — Next.js App Router pages, the only place for `next/navigation`.
- **`apps/desktop/src/renderer/src/platform/`** — the only place for `react-router-dom` wiring.
- If a component is identical between web and desktop, it **must** be in a shared package.
- Use props/slots (`extra`, `topSlot`) on shared layout components to inject platform-specific UI.

### Platform Bridge

- `packages/core/platform/` provides `CoreProvider` — initializes API client, auth/workspace stores, WS connection, QueryClient.
- Each app wraps root with `<CoreProvider>` and provides its own `NavigationAdapter`.
- Shared code uses `useNavigation().push()` or `<AppLink>` — never framework-specific link/router APIs.

## Import Boundaries

**Hard constraints — violating these breaks the cross-platform architecture:**

| Package | May import | Must NOT import |
|---|---|---|
| `packages/core/` | nothing app-specific | `react-dom`, `localStorage`, `process.env`, `next/*`, UI libraries |
| `packages/ui/` | nothing | `@multica/core`, business logic |
| `packages/views/` | `core/`, `ui/` | `next/*`, `react-router-dom`, stores |
| `apps/web/platform/` | `next/*` | other apps |
| `apps/desktop/src/renderer/src/platform/` | `react-router-dom`, electron | other apps |

**Enforcement:**
- ESLint `import-x/no-extraneous-dependencies` rule prevents phantom deps — every import must be declared in the package's own `package.json`.
- CI runs `pnpm typecheck` (all packages) and `pnpm lint` (all packages).

### pnpm Catalog

- `pnpm-workspace.yaml` defines `catalog:` for version pinning of all shared deps.
- All shared deps use `"pkg": "catalog:"` references for single-version guarantee.
- When adding new shared deps (including test deps), add to catalog first.
- Exception: `apps/mobile/` uses pinned versions (not `catalog:`) for packages tied to its React/Expo version.

### Dependency Declaration Rule

Every workspace must explicitly declare all directly imported external packages in its own `package.json`. Relying on pnpm hoist to resolve undeclared imports (phantom deps) is prohibited — it causes production build failures when pnpm creates peer-dep variants.

## API Response Handling

### The parseWithFallback Pattern

All API responses crossing the network boundary must be validated with `parseWithFallback` from `packages/core/api/schema.ts`:

```typescript
import { parseWithFallback } from "../api/schema";
import { TimelineEntrySchema } from "../api/schemas";

// In ApiClient method:
const entries = parseWithFallback(
  await res.json(),
  TimelineEntrySchema,
  [],                          // safe fallback
  { endpoint: "GET /issues/:id/timeline" },
);
```

**Rules:**
1. **Parse, don't cast.** Untyped JSON crossing the network is not `T`. Use `parseWithFallback` with a zod schema and an explicit fallback.
2. **No bare `as` casts on response bodies.** Every endpoint method consumed by UI logic must run through a schema.
3. **Optional-chain and default everywhere downstream.** Treat every field as possibly missing. Use explicit boolean checks (`=== true`) over truthy/falsy.
4. **Enum drift downgrades, not crashes.** A new server-side enum value should render a generic fallback. `switch` statements on server-driven strings must have a `default` branch.
5. **When adding/changing an endpoint:** add the schema in the same PR, write at least one test that feeds a malformed response through it.

### Schema Design (packages/core/api/schemas.ts)

Schemas are intentionally **lenient**:
- String enums use `z.string()` (not `z.enum([...])`) — unknown values still parse.
- Optional fields union with `null` and have fallback defaults.
- Arrays default to `[]`.
- Every object schema ends with `.loose()` — unknown server-side fields pass through unchanged (prevents zod 4's default STRIP behavior from silently deleting future fields).

### Why This Matters

The desktop app installed on a user's machine is older than any backend it talks to. Every response shape is a contract that **will** drift. Three concrete white-screen incidents already happened from violating this: #2143, #2147, #2192.

## Backend Conventions

### UUID Parsing in Handlers

Every Go handler in `server/internal/handler/` follows strict UUID parsing rules. This exists because `util.ParseUUID` used to silently return a zero UUID on invalid input, causing #1661 (DELETE returning 204 success while matching zero rows).

**Three tiers:**

| Function | Use case | Behavior on invalid input |
|---|---|---|
| `parseUUIDOrBadRequest(w, s, fieldName)` | User input at request boundaries (URL params, body, query params) | Writes 400, returns `ok=false` — caller returns immediately |
| `parseUUID(s)` | Trusted round-trips (sqlc-returned UUIDs, test fixtures) | Panics — `chi.Recoverer` converts to 500. Panic = real bug |
| `util.ParseUUID(s)` | Outside handler package | Returns `(pgtype.UUID, error)` — always check error |

**Resource path params that accept UUID or human-readable ID** (e.g., `chi.URLParam(r, "id")` for issues accepting both `MUL-123` and UUID) must be resolved through the dedicated loader (`loadIssueForUser` / `loadSkillForUser` / `loadAgentForUser`). After resolution, all subsequent DB calls MUST use `entity.ID` from the resolved object — never round-trip the raw URL string through `parseUUID` for a write query.

**When adding `Queries.Delete*` or `Queries.Update*` calls:** ask "Where did this UUID come from?" If the answer is "raw user input that hasn't been validated," route it through `parseUUIDOrBadRequest` or a loader first.

### Handler Response Patterns

- Response structs use `json:"snake_case"` tags matching the wire format.
- Helper functions convert sqlc types to response types: `uuidToString()`, `textToPtr()`, `timestampToString()`, `uuidToPtr()`.
- `labelsByIssue` pattern: bulk-load related data to avoid N+1 queries. Returns empty map on error (non-critical data degrades gracefully).

### i18n in Views

- Every JSX text node in `packages/views/` must pass through `useT()` — enforced by `eslint-plugin-i18next` with `mode: "jsx-text-only"`.
- Raw strings in JSX attributes and plain TS literals are allowed.
- Test files (`**/*.test.tsx`) are exempt from i18n rules.
- Translation files: `packages/views/locales/{locale}/{namespace}.json`.
